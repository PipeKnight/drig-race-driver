## Reverse correction

The runtime explicitly initialized the automatic-reverse preference byte `1972` to zero. It also supplied only processed throttle/brake fields, omitting the raw pedal pair used by the existing automatic control helper. This explains the disabled reverse behavior independently of the incomplete collision system.

The runtime now enables this explicit keyboard preference and supplies both raw pedals on each staged tick. Existing verified control arithmetic chooses reverse near rest; no new force or gearbox model was added. Down/S brakes while moving forward, then drives backward near rest. Up/W brakes reverse travel, then selects forward near rest. This is a supplied prototype preference, not proof of reconstructing the original preferences loader.

The source integration test now verifies reverse gear and negative signed forward velocity, return to forward travel, and that braking at forward speed does not immediately select reverse. The Bevy keyboard test also drives backward through the actual ArrowDown mapping. Reset and failure rollback remain checked.

## Handbrake finding

The reported ineffective handbrake has **not been reproduced** in controlled tests. Space is mapped to the existing handbrake command. Starting from the same powered state at tick 120, a 60-tick coast ends near 12.75 m/s; holding handbrake with throttle released ends near 0.0167 m/s. The first handbrake interval produces rear brake terms 3,450 / 3,450 and zero front brake terms; the rear wheels stop rotating. The actual Bevy Space path passes rear-force and near-stop assertions too.

These are scripted source-runtime/keyboard checks, not a diagnosis of the owner's precise input sequence. Existing input-only testing was insufficient to assess braking effect, so the new checks compare physical movement and wheel forces. No speculative physics change was made to the handbrake. The window now shows **HB** for the last accepted handbrake command and **R** for reverse gear, making future feedback easier to interpret.
