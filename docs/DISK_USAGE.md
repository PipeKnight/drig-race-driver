Все размеры здесь логические (сумма длин файлов); после дедупликации жёсткими ссылками логический размер перестаёт совпадать с занятым местом, и тогда реальный выигрыш надо смотреть по свободному месту на диске C:.

**Пока ничего не удалено и не изменено.** Ниже описан план. Каждый шаг выполняется только после того, как владелец явно одобрит конкретный список.

## 7. Профилактика

1. **`build-dir` cargo вне OneDrive.** Предлагаю добавить в `~/.cargo/config.toml`:
   ```toml
   [build]
   jobs = 4
   build-dir = "C:/cargo-build/{workspace-path-hash}"
   ```
   Проверено 16.10 на cargo 1.99.0 (тестовый проект в scratch): промежуточные `deps`/`incremental`/`build` уходят в `build-dir`, а итоговый `.exe` остаётся в `target/`. Ярлыки и `tools/update_prototype.ps1` продолжают находить `target/release/grid-app.exe`. Каждый worktree получает свою подпапку (хеш пути), так что сессии не блокируют друг друга. Цена: один раз всё пересоберётся. Общий для всех `CARGO_TARGET_DIR` **не рекомендую**: параллельные сессии с разными ревизиями будут ждать блокировку сборки и пересобирать друг за другом. Когда worktree удалён, его подпапка в `C:\cargo-build` становится сиротой и удаляется вручную (`tools/disk_report.ps1 -Children C:\cargo-build`).
2. **Меньше отладочной информации.** `.pdb` занимают 9,0 из 16,5 ГиБ в `target/debug` основной копии и 10,4 из 18,2 ГиБ в `magical-cray`. Предложение для `Cargo.toml` (решает владелец: изменение общее и вызовет пересборку у всех сессий):
   ```toml
   [profile.dev]
   debug = "line-tables-only"
   [profile.dev.package."*"]
   debug = false
   ```
   На генерируемый код и детерминизм это не влияет. Ожидаемое сокращение отладочных каталогов примерно вдвое — это оценка, не замер.
3. **Жизненный цикл worktree.** Когда координатор переводит сессию в архив, удалять `target/` её worktree. Если ветка влита и изменений нет, удалять и сам worktree (`git worktree remove`). Раз в день запускать `tools/disk_report.ps1`.
4. **Правило хранения `local/` для захватов:**
   - после проверки сразу запускать `tools/dedup_hardlinks.py` на новую папку (debug/release/native и повторы ничего не стоят);
   - черновики `draft-NN`, когда записан процитированный `final`, оставлять только как `failure.md`/`validation.json`, сырые `.bin` удалять;
   - вытесненный `final-01`, если процитирован `final-02`: та же схема;
   - всё, что цитируется в записях, хранить полностью;
   - раз в неделю: `disk_report` → `classify_behavior_captures` → список кандидатов на одобрение владельцу.
5. **Зонды** могли бы сохранять сырые дампы только при расхождении, а при совпадении записывать хеш. Это изменение инструментов, отдельная задача.

## 8. Неопределённости

- Классификация «не процитировано» основана на текстовом поиске имён. Если ссылка в записях имеет форму, которую поиск не распознаёт (например, имя собрано по частям в скрипте), такая папка попадёт в кандидаты. Поэтому шаг 4 идёт отдельным одобрением и после шага 3.
- Статус «работает»/«простаивает» снят около 06:00 16.10 и перед удалением проверяется снова.
- Нагрузка от `OneDrive.Sync.Service` — наблюдение без установленной причины.
