# Использование диска и план очистки

Замер 16 октября 2026, Claude Code (сессия очистки диска). Единицы: ГиБ = 2^30 байт, так же их показывает Проводник Windows («ГБ»). Все размеры здесь логические (сумма длин файлов); после дедупликации жёсткими ссылками логический размер перестаёт совпадать с занятым местом, и тогда реальный выигрыш надо смотреть по свободному месту на диске C:.

**Шаги 1–3 одобрены владельцем 16.10 и выполнены; итог в разделе 0.** Разделы 1–6 описывают замер, сделанный до очистки. Шаги 4 и 5 владелец не одобрил, они не выполнялись.

## 7. Профилактика

Одобрено владельцем и внедрено координатором 16.10 (запись F328): `build-dir`, профиль dev, правило хранения в `AGENTS.md`, очистка `target/` при архивации сессии.

1. **`build-dir` cargo вне OneDrive.** Предлагаю добавить в `~/.cargo/config.toml`:
   ```toml
   [build]
   jobs = 4
   build-dir = "C:/cargo-build/{workspace-path-hash}"
   ```
   Проверено 16.10 на cargo 1.99.0 (тестовый проект в scratch): промежуточные `deps`/`incremental`/`build` уходят в `build-dir`, а итоговый `.exe` остаётся в `target/`. Ярлыки и `tools/update_prototype.ps1` продолжают находить `target/release/grid-app.exe`. Каждый worktree получает свою подпапку (хеш пути), так что сессии не блокируют друг друга. Цена: один раз всё пересоберётся. Общий для всех `CARGO_TARGET_DIR` **не рекомендую**: параллельные сессии с разными ревизиями будут ждать блокировку сборки и пересобирать друг за другом. Когда worktree удалён, его подпапка в `C:\cargo-build` становится сиротой. Удалять её вручную на практике забывали, и к 19.10 сироты заняли 82 ГиБ. С тех пор их убирает `tools/prune_build_dirs.ps1` (раздел 9).
2. **Меньше отладочной информации.** `.pdb` занимают 9,0 из 16,5 ГиБ в `target/debug` основной копии и 10,4 из 18,2 ГиБ в `magical-cray`. Предложение для `Cargo.toml` (решает владелец: изменение общее и вызовет пересборку у всех сессий):
   ```toml
   [profile.dev]
   debug = "line-tables-only"
   [profile.dev.package."*"]
   debug = false
   ```
   На генерируемый код и детерминизм это не влияет. Ожидаемое сокращение отладочных каталогов примерно вдвое — это оценка, не замер.
3. **Жизненный цикл worktree.** Когда координатор переводит сессию в архив, удалять `target/` её worktree. Если ветка влита и изменений нет, удалять и сам worktree (`git worktree remove`). Раз в день запускать `tools/disk_report.ps1`.
4. **Правило хранения `local/` для захватов:**
   - после проверки сразу запускать `tools/dedup_hardlinks.py` на новую папку (debug/release/native и повторы ничего не стоят);
   - черновики `draft-NN`, когда записан процитированный `final`, оставлять только как `failure.md`/`validation.json`, сырые `.bin` удалять;
   - вытесненный `final-01`, если процитирован `final-02`: та же схема;
   - всё, что цитируется в записях, хранить полностью;
   - раз в неделю: `disk_report` → `classify_behavior_captures` → список кандидатов на одобрение владельцу.
5. **Зонды** могли бы сохранять сырые дампы только при расхождении, а при совпадении записывать хеш. Это изменение инструментов, отдельная задача.

## 8. Неопределённости

- Классификация «не процитировано» основана на текстовом поиске имён. Если ссылка в записях имеет форму, которую поиск не распознаёт (например, имя собрано по частям в скрипте), такая папка попадёт в кандидаты. Поэтому шаг 4 идёт отдельным одобрением и после шага 3.
- Статус «работает»/«простаивает» снят около 06:00 16.10 и перед удалением проверяется снова.
- Нагрузка от `OneDrive.Sync.Service` — наблюдение без установленной причины.

В папках `%TEMP%\claude` лежат логи фоновых задач на 1,6 и 0,75 ГиБ, копии Ghidra-проекта и `vd-target`. Самые свежие файлы там от 16.10.

**Причина.** Каждая копия собирает в свою папку `C:\cargo-build\{хеш пути}` (F328). При архивации сессии координатор удалял `target/` и сам worktree. Но после F328 в `target/` остаются только итоговые exe. Промежуточная сборка, от 2 до 11 ГиБ на копию, лежит в `C:\cargo-build`, и `git worktree remove` её не удаляет. Так же остаются папки сборки временных worktree, которые сессии создают для проверок. Правило «удалять вручную» из раздела 7.1 не выполнялось.

**Как сопоставлено.** Для каждой копии из `git worktree list` команда `cargo metadata --format-version 1 --no-deps --offline` сообщает её `build_directory`. Остальные папки вида `XX\<14 hex>` считаются сиротами. По содержимому папки владельца не определить: пути к исходникам в dep-info относительные.

**Сделано.** Написан `tools/prune_build_dirs.ps1`. По умолчанию это пробный прогон, `-Apply` удаляет.
- Живые папки скрипт берёт из `git worktree list` и `cargo metadata`.
- Сирота с файлом моложе `-MinIdleHours` (по умолчанию 6 ч) остаётся: в неё может собирать scratch-проект, который не является worktree.
- `seed` и другие именованные папки скрипт не трогает.
- `-ForWorktree <путь> -Apply` удаляет папку сборки одной копии. Запускать **до** `git worktree remove`.

Пробный прогон дал тот же список, что ручное сопоставление. Прогон с `-Apply` удалил 20 папок на 73,97 ГиБ: `01, 2b, 48, 4b, 6c, 77, 80, 81, 9c, a0, a7, aa, be, e0, ea, f9`, обе папки в `fe`. Последние изменения в них были с 16.10 15:00 по 18.10 15:22. Удалены и 7 пустых родительских папок. По правилу 6 ч оставлены две папки, их уберёт следующий прогон:
- `21\038a71657892fc`: 3,80 ГиБ, изменена 18.10 в 22:18;
- `7d\2d85bebf568e06`: 4,11 ГиБ, изменена 18.10 в 23:07.

Свободно на C: стало **125,3 ГиБ**. Во время удаления в живых worktree шли три тестовые сборки; их папки не тронуты.

**Профилактика.**
- При архивации сессии: `prune_build_dirs.ps1 -ForWorktree <worktree> -Apply` перед `git worktree remove`.
- При периодической проверке лимитов координатор запускает `prune_build_dirs.ps1 -Apply`.
- Правило записано в `AGENTS.md`.
