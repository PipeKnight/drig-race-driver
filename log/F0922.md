F922 GPU unit tests run in their own process: NVIDIA D3D12 driver crash in the grid-app test process (2026-11-25, Claude Code).
- Task (coordinator): find the root cause of the intermittent 0xc0000005 that killed the grid-app test process in G433 (source 5bab76cc) and the first full gate of F906 (local/prepush/20261124-191951 in the sweet-sinoussi worktree). Windows event 1000 named `nvwgf2umx.dll` 32.0.16.2101 at +0x8040b2, the NVIDIA D3D10/11/12 user-mode driver. Hiding it with RUST_TEST_THREADS=1 or by dropping tests is not a fix.
- Diagnosis tool (new, kept): `crates/grid-app/src/test_crash_report.rs`, compiled only in grid-app Windows test builds. A vectored exception handler is installed before `main` through `.CRT$XCU`, like `mobile::INIT_TEST_POOL`. On an access violation it writes the faulting module and offset, the access, the thread id and name, and up to 48 stack frames as module+offset to stderr, then lets the exception continue. It writes with WriteFile and takes no Rust lock.
- Repro script (new): `tools/test_crash_repro.ps1` runs one test binary N times under the build lock with prepush's GRID_* inputs, with RUST_TEST_THREADS unset. It matches each crash to its event 1000 by process id, copies the handler's report, and samples every 20 s whether `-WatchModule` (default nvwgf2umx.dll) is loaded in the test process. It prints one verdict line. Two fixes during the work:
  - build_lock passes an array parameter as one comma-joined argument, so filters are split on commas, and a run that matches no test throws;
  - the hex format of a negative exit code was fixed.
- Observations. Old exe: 9dd24bbf build dir, grid_app-fbab7f941c092e93.exe, source 9d026a6b plus the handler.
  - The suspect set alone never crashed. Filters were pane_slab's device test, pause_menu, replay and flashback race tests (44 tests); 10 runs, mean 71 s.
  - The whole binary (1039 tests, `--include-ignored`, parallel) crashed in **3 of 24 runs**: run 4 of a first batch of 4, run 5 of 17, and run 1 of 3. Every crash was the same: nvwgf2umx.dll+0x8040b2, a read of freed heap memory, on one or two **unnamed driver threads** whose stack is nvwgf2umx+0x8040b2 ← +0x804069 ← +0xfd2d56 (thread entry) ← KERNEL32 BaseThreadInitThunk. No test thread was involved.
  - Each crash came 2-5 minutes after `pane_slab::tests::copies_run_only_where_standard_material_is_bindless` had passed (line ~25 800 of ~202 800 output lines), during the flashback race tests. That test is the only unit test in the workspace that opens real devices: Vulkan twice and D3D12 once, all dropped at its end (F881, 2026-11-20). The crashes began on 2026-11-23.
  - In all 3 watched runs, nvwgf2umx.dll was loaded in the test process from ~20 s until the end.
- Interpretation: the D3D12 driver keeps worker threads after the test drops its device, and they later read freed memory. Heap churn from the parallel race tests makes the read fault. This is a driver defect that our code cannot fix in the driver. The game itself opens one device per process and keeps it (`front_end_host`), so it does not reach this path. The root fix on our side is that a test's device and driver threads never share a process with other work.
- Fix:
  - `crates/grid-app/src/gpu_test_process.rs` adds `in_own_process(body)`. Called from a libtest test thread, it re-runs the same test binary with `<test path> --exact --include-ignored --nocapture --test-threads=1` and `GRID_GPU_TEST_CHILD` set. It echoes the child's output and asserts the child exited successfully with exactly one passed test. In the child it runs `body` directly.
  - The pane_slab device test now runs through it.
  - The guard test `gpu_test_process::tests::device_tests_run_in_their_own_process` scans every `#[cfg(test)]` module in `crates/*/src`, inline or in its own file (409 modules today), for device code: `request_device(`, `enumerate_adapters(`, `request_adapter(`, `RenderPlugin`, `DefaultPlugins`, `RenderCreation::`. It fails when a module with device code does not call the helper.
  - Integration tests in `crates/*/tests/` are separate processes and already do only GPU work: atmosphere_ssao_bind_groups, bin_buffer_upload, bind_group_cache and environment_map_switch have one test each, and bind_dedupe renders in child runs. They are unchanged.
  - CPU tests stay parallel.
  - docs/TOOLCHAIN.md has a new section, "Tests that open a GPU device".
- Verification. New exe, same build dir; the binary now has 1040 tests.
  - The two changed tests pass (4.6 s together).
  - The whole binary in parallel had **0 crashes in 23 runs**: 17, then 6 with the watch. **nvwgf2umx.dll was never loaded in the test process in 6 of 6 watched runs**, against 3 of 3 before. That is the deterministic part: the driver that faulted is no longer in the process.
  - At the old rate of 3 in 24, 23 clean runs would happen by chance with p≈0.05.
- Cost: whole-binary mean 278 s before against 274 s after (17 runs each, same period, machine shared with other sessions), so no measurable difference. pane_slab device test alone (whole binary filtered to it, 3 runs): 1.82, 1.04, 1.04 s before against 1.14, 1.26, 1.20 s after, so the child process adds about 0.2 s to that one test.
