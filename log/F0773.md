- Window-show hang (latent since F756, shared by every screen and the race):
  - Cause: `transition::handoff_ready` set `Window.visible` in `Last`, unordered against bevy_winit's `changed_windows` (also `Last`). When `changed_windows` ran first, the change was never applied: winit kept the window hidden, a hidden window gets no `RedrawRequested`, and with Bevy's `Window` already visible, bevy_winit 0.19 ran no further update on Windows.
  - Any added `Last` system can reorder them. An F773 draft with a sound system in `Last` hung 3 of 3 menu screens with sound, 0 of 3 with `GRID_AUDIO=off`, and 0 of 3 at F756.
  - Main-thread stack (dbghelp `StackWalk64`, new `tools/stack_sample.ps1`): spinning in winit `about_to_wait` → `create_monitors`/`NtUserEnumDisplayMonitors` and `RedrawWindow`.
  - The career-ui report fits the same cause: `frame_pacing::window_shots` is a `Last` system, and it is installed only when `GRID_WINDOW_SHOTS` parses, which matches "no frames, one busy core, still responding".
  - Fix: `add_window_show` registers `handoff_ready` in `PostUpdate`. Test `the_shown_window_reaches_last_on_its_frame`. After the fix, the same A/B opened 3/3 in every case.
  - On this branch before the rebase, `--menu-screen` with `GRID_WINDOW_SHOTS` = 2, 0 and 0.1,3 saved every shot and kept drawing. The report itself was not reproduced on main's build (the build lock was busy and no main executable was kept), so that it is the same hang is [I] until career-ui reruns on this commit. On this commit with `GRID_AUDIO=off GRID_WINDOW_SHOTS=1,3` for 20 s: `--career-screen` and `--menu-screen` each saved 2 of 2 shots and faded in (`local/menu-loop/f773/career-screen`, `menu-screen`).
