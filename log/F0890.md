F890 grid-app test compute pool created at process start (TaskPool stack overflow root cause) (2026-11-23, Claude Code).
- Task (coordinator): root cause of the intermittent STATUS_STACK_OVERFLOW in the grid-app tests that made the full prepush gate fail about two runs in three without `RUST_MIN_STACK=64 MiB` (F638, F642, F702, F705, F706, F710, G328, G363, F886).
- Observation: all four overflows still on disk name a `TaskPool (N)` thread: mac-perf `local/prepush/20261123-105751` and `20261123-112852` (07-test-workspace.log, right after `pause_menu::race_tests`), strange-chatelet `local/prepush/20261119-005406` (03-test-grid-app.log) and `20261119-123809`. grid-app builds its pool as "Compute Task Pool" (`mobile::init_compute_pool`) and grid-tools as "grid compute"; `TaskPool (N)` is the name bevy_tasks 0.19.1 gives a builder without a thread name.
- Cause [V from source, I for which test wins]: bevy_ecs 0.19.1 `schedule/executor/multi_threaded.rs:274` runs systems on `ComputeTaskPool::get_or_init(TaskPool::default)`: the first schedule run of a process without a pool creates one with every core and the std default stack (2 MiB unless `RUST_MIN_STACK`). The first pool of a process stays. F632 made test Apps call `init_test_pool` (64 MiB) first, but only 15 call sites did; the grid-app tests have 107 `App::new()`. libtest runs them in parallel, so whichever test reached the pool first decided the stack of every test in the process. When one without the call won, nested `drive_tick`s of the parallel race tests (a thread waiting in `parallel::map`'s scope runs other Apps' ticks on its own stack, 0.5–0.75 MB each, F632) overflowed 2 MiB. `RUST_MIN_STACK` hid it by raising the std default.
- Fix (`crates/grid-app/src/mobile.rs`, tests only): the test binaries create the 64 MiB compute pool once at process start, before libtest runs any test, through a static in the C runtime initializer table (`.CRT$XCU` on Windows, `.init_array` on Linux/Android, `__mod_init_func` on Apple; no new dependency). The initializer only calls `available_parallelism` and spawns the pool's threads; it does not touch `thread::current` on the main thread, which std sets up in `main`. The 15 per-test `init_test_pool()` calls are gone (engine_sound, main.rs driving tests, race_tests, scene_probe, source_trees, tyre_sound, ui_font). The game's pool (`init_threads`), thread counts and the simulation are unchanged.
- Test: `mobile::tests::test_apps_get_the_large_stack_compute_pool_before_any_test`: the pool exists (`ComputeTaskPool::get` panics otherwise), a task spawned on it runs on a `Compute Task Pool (N)` thread, and it has one thread per core. Run alone with `--exact` (no other test can create the pool first): 1 passed, so the initializer runs before main with rust-lld.
- First full gate, with this change (`local/prepush/20261123-130538`): sanity, clippy-workspace, build-grid-app, render-smoke, build-race-soak and identity passed (solo, 12-car, 12-car-df and derby-df unchanged). test-workspace never ended: by 14:10 every test had finished except `pane_slab::tests::copies_run_only_where_standard_material_is_bindless` (F881), which libtest reported "running for over 60 seconds". The gate held the build lock for 172+ minutes, until the owner restarted the PC because several jobs had hung. Output was captured, so the log does not show whether the test stopped in instance creation, adapter enumeration or device creation (it prints only after all three devices exist). No stacks were taken.
