F995 Dynamic resolution: a frame that only waited for the display is not late (2026-11-27, Claude Code).
- Follows F985 (the pacer's acquire-free frame work); requested by the owner through the coordinator as a separate commit. The change is general (every platform, track and car) and touches only `crates/grid-app/src/render_scale.rs`: no simulation code, no render pass.
- Evidence (F981, the owner's Mac traces): GPU 2 ms and acquire 9-11 ms per frame at vsync; dynres "late" steps moved at smoothed frame times of 17.6-18.4 ms between 1224 and 1440 rows. The swap-chain wait is a display wait there, and no height changes it.
- Rule (`Dynamic::update`):
  - `busy_ms` smooths the frame time without the acquire wait (SMOOTHING 0.1).
  - A smoothed frame time above `LATE_MS` (18) but at most `NEAR_MS` (1.25 × `TARGET_MS`, 20.8 ms: one missed refresh) with `busy_ms <= ON_TIME_MS` (17.2) is display-bound and does not count as late.
  - Beyond `NEAR_MS` a frame is late whatever its wait, so a GPU-bound frame that waits in acquire (Metal, F929) still steps down.
  - F932's GPU_LATE_SHARE rule (time over the target from frames that waited in acquire counted as late inside the 17.2-18 ms band) is removed with `gpu_late_ms`. The band holds again, as before F932.
  - Step size, warm-up, probe, blocks and `cpu_bound` are unchanged.
- Not subtracting the whole wait was a deliberate choice: on Metal and with wgpu's latency waits a GPU-bound frame also waits in acquire, so full subtraction would stop dynres on GPU-bound 60 Hz machines. Trade-off [I]: a GPU-bound frame of 18-20.8 ms that waits in acquire now holds where it stepped down before. Phones wait in present rather than acquire (F981) and run far above `NEAR_MS`, so they are unaffected.
- Log: `render_dynamic version=5`; change lines print `busy_ms=` instead of `gpu_late_ms=`; the install line prints `display_bound=near_ms+on_time_ms` instead of `gpu_late_share=`. No tool parses the removed fields (grep of tools/).
