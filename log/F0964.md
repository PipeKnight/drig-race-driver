F964 Refresh-divisor frame pacing for all platforms (macOS, Android; Windows opt-in) (2026-11-26, Claude Code).
- Cause (F958): on the owner's 120 Hz Mac 15 ms frames present on 8.3/16.7/25 ms intervals under Fifo (27-28 % of race frames >= 20 ms) instead of an even 60. The F958 GPU columns were invalid; with valid timing the GPU takes about 2 ms and the frames wait for drawables (below).
- New shared pacer `crates/grid-app/src/refresh_pace.rs`, one code path for every platform, installed for the standalone race and the hosted front end. Once a second it reads the display's actual refresh rate: Android JNI first, otherwise winit `current_monitor()` of the window, falling back to `primary_monitor()` (macOS reports no current monitor at window creation, `monitor_hz=[]` in F958), `refresh_rate_millihertz()`, so a move to another screen is followed. A change of more than 0.5 Hz returns to plain vsync and logs `refresh_pace display_hz=.. was=..`. 120 Hz is never assumed.
- Rule (`Pacer::second`): candidates are R/n with R/n >= 59.5 Hz, so 60/75/100 Hz screens keep plain vsync (no 30 FPS cap), 120 -> 60, 144 -> 72, 165 -> 82.5, 240 -> 120/80/60.
  - A rate holds while the mean interval <= period x 1.1 (`KEEPS_UP`) and, when paced, the p90 work (interval minus the pacer's own sleep) <= period x 1.1 (`OVERRUN`).
  - Not holding for 2 s moves to the fastest slower open rate that fits the mean (`ENGAGE` 1.0, from vsync, which rounds frames up to whole periods) or the p90 work x 1.1 (paced), else back to vsync.
  - The rate it leaves, plain vsync included, is blocked for 20 s, doubling to 160 s per rate, so a presentation-limited 120 is not retried every few seconds.
  - A faster open rate is taken after 5 s with margin x 1.25.
  - The first draft engaged only when mean x 1.2 fit a slower period; with the Mac's 15.3 ms mean (15.3 x 1.2 > 16.67) it would never have engaged, so the rule was reworked after the traces below.
  - Hitches > 250 ms are skipped.
- Setting `[video] refresh_pacing = auto|on|off` (docs/SETTINGS.md). `auto` is on for macOS, iOS and Android and off on Windows and Linux, where VRR screens and the owner's 165 Hz PC at 100+ FPS gain nothing, so desktop Windows behaviour is unchanged. Only Fifo, FifoRelaxed and AutoVsync are paced.
- Android: the fixed `[video] refresh_hz` cap and the thermal cap (F378, F935) now go through the same pacer (`android_display::cap` sets `RefreshPace::set_cap`, the lower of cap and pace wins); the old sleep in `Last` is gone. `refresh_hz = System` now gets the divisor pace.
- ProMotion: wgpu exposes neither `presentAfterMinimumDuration` nor CAMetalLayer/CADisplayLink preferred frame rate ranges, so the pace is a sleep before present (`render_scale::pace`), as on Android. Documented in docs/PERFORMANCE.md "Refresh pacing (F964)".
- Dynres still targets 16.67 ms; at a 60 pace the two agree. The 72/82.5 paces hold only while the frame already fits.
- Logs: `refresh_pace mode=.. enabled=.. cap_hz=..` at start, `refresh_pace display_hz=.. pace_hz=..|vsync mean_ms= work_p90_ms=` per change, `pace_hz=` in each `frame_stats` line, `refresh_pacing=` in `frame_setup`.
