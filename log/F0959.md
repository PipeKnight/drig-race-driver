F959 Metal GPU timestamps fixed (owner PR 87) (2026-11-26, Claude Code).
- Owner commit e06af0db (PR 87, branch codex/macos-metal-gpu-timings), crates/grid-app/src/frame_split.rs. On Apple M4 the empty compute pass used as a GPU marker left its timestamp at zero, and a resolve made too early sometimes returned the slot's previous timestamp. All 310 windows of each 1546e211 Mac trace (Donington, Istanbul) had invalid GPU timing (F958 marks those columns invalid).
- Fix, Metal only: markers are written with `write_timestamp` plus a 4-byte `clear_buffer` (a non-empty blit pass); a slot is resolved only after `queue.on_submitted_work_done` signals that its command buffers finished (new `Submitted` state, ring of 6 slots instead of 3); Metal needs TIMESTAMP_QUERY_INSIDE_ENCODERS, else GPU timing reports `no_metal_encoder_timestamp`.
- All backends: ticks of 0 or u64::MAX count as bad, and a frame with any bad tick is left out of the GPU averages (it still counts in g_bad); `g_frames/g_bad/g_lost` print whenever any is non-zero. New test `invalid_gpu_frame_is_excluded_from_timing_averages`. Windows (D3D12) and Android (Vulkan) keep the empty compute-pass markers and same-submission resolve.
- Owner's measurement after the fix (traces drig_trace_*_metal_fixed_1546e211_20261126_*): 0 invalid intervals and 0 lost readback buffers on both tracks. The analysis of those traces goes to the mac-perf session.
