F379 P12 part 1: the 12-car tick's per-car stages run on several cores, bit-identical to the serial tick (2026-10-18, Claude Code). Details, profile and numbers: docs/PERFORMANCE.md (docs/TICK_PERFORMANCE.md points there). Evidence: worktree focused-torvalds-7a0b54 `local/perf/` (before/after outputs, measure/, app/ trace summary, tests/clippy logs; the 1.5 GB trace JSON deleted after summarising).
- Measured first [V]: the headless 12-car race's tick is about 66 % of the race thread. Inside the tick the vehicle stage is 0.62 ms of 0.89 ms, body contacts 0.13, car pairs 0.07, solver 0.03, commit 0.02; AI drivers about 0.1 ms. Desktop app (12 cars): main schedule about 4.6 ms per frame, of which `drive_tick` 2.2 ms. Render thread about 5–7 ms per frame. Bevy 0.19.1 `trace_chrome` trace: `allocate_and_free_meshes` 1.0 ms and `prepared_mesh_producer` 0.44 ms per frame, so about 13 mesh assets are re-uploaded every frame. Loading 12 cars takes 6–10 s, about 85 % in each car re-parsing the route props (`Props::read_route`).
- Change: `grid_tools::parallel::map` (results in index order on Bevy's `ComputeTaskPool`, which the app and the headless tools share; new dependency bevy_tasks =0.19.1, already in the tree). `MultiRuntime::tick` runs every car's vehicle stage, body contacts and car-pair hulls/rows at once, then an ordered pass keeps the pool offset (`wheel_contacts::overlay` places contacts produced into a blank pool), capacities (`BodyGeometry::reusable_with`, pair capacity min 16) and failures in serial order. `MultiRuntime::parallel` (default true); `GRID_THREADS=N` caps it (1 = serial, the app too). The solver, prop pieces, commit and AI stay serial.
- Diagnostics: `GRID_PERF_TIMING=1` (grid_tools::perf; grid-app prints `perf_timing` every 600 frames and at exit, grid-opponent-race on stderr); grid-app feature `trace` (bevy/trace_chrome, adds tracing-chrome 0.7.2 to Cargo.lock, off by default); tools/chrome_trace_summary.py.
