- Damage rule check (owner, 2026-11-20; coordinator's five points), from the code of `drive_present`:
  1. Only presentation waits. The `continue` sits in the opponent loop that compares each car's field key and
     fills the list of meshes to re-project. It runs after the simulation tick and writes nothing back to it.
     Part poses, the player's projection (the block above it) and the simulation are not behind the switch.
  2. The final dent state is the same. A projection is a pure function of the car's current field (policy
     `independent-current-minus-rest`), not an increment. The deferred car keeps its old key, so the next frame
     reads the then-current field and projects exactly what an undeferred frame would. Images: the offscreen
     derby frames at ticks 1500 / 2400 / 3600 differ by 1 / 2 / 0 pixels, max delta 1. The capture frame can be
     a deferring one.
  3. No impact is skipped or merged in the simulation; contacts, damage and the field are untouched. On screen,
     the field of a deferred frame is shown one frame later, together with that frame's tick. That is the same
     as when two fixed ticks fall in one render frame, which already happens without the spread.
  4. Detachment is not delayed: it runs in `damage_parts`, a separate system that does not read the field keys
     or `DentSpread`. The player's dents are projected in the same frame as before.
  5. `GRID_DENT_SPREAD` is read once per run. It is stored in the system's `Local<DentSpread>` on the first
     frame (`get_or_insert_with`), as `GRID_DENT_FAST` is next to it.
  - Worst-case added latency: one frame. A frame after a deferring one projects whether or not it ticked (test).
