F767 One-window front end: menu, loading screen and race in one process (2026-11-09, Claude Code).
- Task (coordinator, owner away): Menu → Loading → Race → Menu in one process and one window, with a loading screen; no leaks between races; keep the launchers, `--menu`, the gate's `menu-default` and Android working. Research and design: [docs/FRONT_END_FLOW.md](../docs/FRONT_END_FLOW.md) (original's state graph, loading screen content, executable findings, symbols.tsv rows; section 5 is the AUTHORED port state machine).
- Design (AUTHORED): winit allows one event loop per process, so `grid-app --menu` now runs a small host app (`crates/grid-app/src/front_end_host.rs`) that owns the window, the event loop, input and the one gamepad backend, and a `FrontEnd` state (`Starting, Menu, Loading, Race`) for the main-menu shell to build on. Every screen stays its own Bevy app (`event_menu::screen_app`, new `loading_screen::app`, `race_app` split out of `run` in main.rs), built with `hosted()` plugins on a `front-end-build` thread while the previous screen or the loading screen is up, attached by giving it the outer window's raw handle, and dropped whole on leaving (world, assets, GPU resources, render thread, audio output). Window and gamepad messages are forwarded with entities remapped; size, focus and cursor go in, the title out. Exit codes as before: `MENU_GO` 20 builds the race, `BACK_TO_MENU` 21 the menu. The F726 pipeline warm-up runs inside each race app unchanged.
- Loading screen: built at the same time as the next screen, attached first, kept up at least 0.8 s (the stat panel's `on_time` minimum); fade from black 0.5 s, `loading` label, a 12-dot load circle. Not ported: the 3D tarmac world, the `fact_*` stat panel, the fade to black before leaving a screen.
- Root cause 1 (hang after the loading screen attached): Bevy's `MainThreadExecutor` belongs to the thread that creates it and is ticked only there; made on the build thread, the `NonSendMarker` systems (`tick_global_task_pools` in `Last`) never ran and the first update waited for ever. Builds now stop after `finish()`; `attach` makes the executor on the main thread and only then runs `cleanup()` (render world copy, render thread).
- Root cause 2 (thread and handle growth per race, found with a per-name thread census at each menu): gilrs 0.11.2 starts a force-feedback server thread per `Gilrs` instance whose loop ignores the closed channel (`ff/server.rs`), so every screen's `GilrsPlugin` left one `gilrs` thread behind (2 per race, about 37 handles). Fix: `GilrsPlugin` only in the host; `hosted()` disables it; the host forwards each pad's connection, button and axis messages, raw and typed, with the pad as an entity of the screen's world, replaying the connection of pads present at attach.
- Root cause 3 (handles +35 per race after the gilrs fix, found with a per-type handle census, `handle_types=`): the NVIDIA Vulkan driver (621.01, RTX 4070) leaves kernel objects behind for every destroyed device (per app: 2 Mutant, 2 Section, a Semaphore, a Timer, plus events). Fix: one render device per kind of screen (`Gpu::Ui` menu and loading screen, `Gpu::Race`), kept by the first screen of that kind and given to later ones through `RenderCreation::Manual(RenderResources)`. Kept devices outlive their apps and wgpu frees a dropped app's resources only when its device is polled, so sharing alone grew 822 → 2267 MB over 6 races; `reclaim_devices()` waits on the kept devices whenever the host drops a screen. Side effect: loading screen and menu builds fell from ~1 s to 0.08/0.13 s.
- Host plugins are the minimum (window, winit, input, gilrs, time, task pools, log, states, assets for the cursor): a host renderer without a GPU backend logged `Render app did not exist` errors.
- Kept outside the host: `--settings` launchers run the race directly as before; `GRID_FRONT_END=processes` keeps the older per-process supervisor; the career screen keeps its supervisor; Android keeps relaunching the activity per screen (a NativeActivity owns its loop and surface; host path not verified there); Restart stays in place inside the race.
- New smoke `tools/front_end_loops.ps1` (`GRID_MENU_LOOPS=N`, `GRID_MENU_AUTO`): menu → race → menu N times in one process; each menu prints private MB, handles, threads (with names) and host entities; default 8 races × 300 ticks; verdict (AUTHORED): ≤ 48 MB and ≤ 40 handles growth per race from the middle menu to the last (the first races fill caches and the kept devices' allocators), threads ≤ the middle menu's + 2, host entities unchanged, ≥ 5 menus. The build gate runs it as `front-end-loops`, alone after its queue (tools/build_gate.ps1, TOOLCHAIN.md).
- Merged with F756 (screen transitions, on main first): every screen app keeps F756's overlay fade and hidden-until-frame-3 window; a hosted race gets `--from-menu`, so F756's launcher-to-menu path (`MENU_AFTER` → `event_menu::supervise` after the race app) stays for `--settings` races only (a second winit loop cannot start in that process). The host counts menu rounds in `event_menu::HOST_ROUND`, so `GRID_MENU_AUTO_RACES` and `tools/menu_loop_smoke.ps1` end the same way under the host as under the supervisor (`GRID_MENU_ROUND`).
