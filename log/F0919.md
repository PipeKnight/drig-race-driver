F919 Phone proxy: predicted Xiaomi frame from a phone-like desktop run (2026-11-25, Claude Code).
- Task (coordinator): predict, within minutes and without the phone, whether a source change makes the owner's Xiaomi 13 Ultra frame faster or slower and by about how much. The owner rejected adb and phone-in-the-loop runs, so the phone's logs of 24 November (F912, F915) are the only ground truth. Method, tables and limits: docs/PERFORMANCE.md "Phone proxy: the phone's frame predicted from a desktop run (F919)".
- New `tools/phone_proxy.ps1` and `tools/phone_proxy.py`, plus `tools/phone_proxy_calibration.json`:
  - `-Rev <commit> -Compare <commit>` (or `-Exe`/`-CompareExe`) builds each commit through the build lock in a side worktree (`local/phone-proxy/src`, exes cached in `local/phone-proxy/bin`). It never builds or runs the main checkout's prototype.
  - It runs the phone's race on the desktop: the bundle's settings.ini and Donington event.ini (12 Lacetti, chase camera), `GRID_MENU_AUTO`, autopilot, `GRID_MOBILE_PRESET=1`, `GRID_COMPUTE_THREADS=6`, indirect-call validation as on Android, feature `profile`, 480 rows (768 × 480 in the default window), muted.
  - The process is pinned with `start /affinity <mask>`, per process and reversible; no power or system setting is changed.
  - Defaults: mask F0000 (the four E-cores), 3 runs of the normal state per revision, alternating, under one lock hold. A run takes about 75 s.
  - It maps the desktop's 1 s `frame_stats` medians to the phone per component (non-sim main, per-tick sim × ticks per frame solved as a fixed point, render busy, GPU; frame = max + gap). It prints the predicted phone split, the delta, the platform-independent counters that moved, and a noise limit, and ends in one VERDICT line.
  - `-SelfTest` is the smoke step: the analyser selftest and argument handling, with no build or run. `-CheckOnly -OutDir` re-analyses a run.
- Calibration [O] (APK source 57c966e1, profile exe, sha256 f54387123665d41f…; HEAD 94b4f286 exe c0f6ef08279edf51…):
  - Masks F0055, F0000, F0005 and FFFFF, one run per state each. F0055 and F0000 were also pooled with a second run.
  - Largest error of the predicted phone frame over the three states: 4.5 to 6.4 ms.
  - Shipped: F0000 pooled. Ratios main non-sim 2.27, per tick 1.75, render busy 2.05, GPU 6.94, gap 6.5 ms. Predicted 45.3 / 39.2 / 35.3 ms against the phone's 40.3 / 38.9 / 40.5 ms; largest error 5.2 ms.
  - Affine fits may only have a positive slope. F0005 and FFFFF had chosen negative slopes for main non-sim, which only follow phone noise.

- A/B reproduction [O/I]: partial.
  - Shadows off: the phone has -1.4 ms; the proxy has -6.1 ms (F0000) or +5.8 ms (F0055), both within the GPU residual.
  - Whole scene off: the phone is flat (+0.2 ms); three of four masks predict it 3-10 ms faster (FFFFF +0.4). The desktop gains 16-25 % fps from an empty scene; the phone gains nothing.
- Reading for the main-thread work [I]:
  - The phone's render-busy time is flat across the three states (28.4 / 27.0 / 28.8 ms), and its non-sim main time rises from 16.8 to 21.1 ms with the scene removed. So most of the phone's frame is a fixed per-frame cost (executor hand-offs and wake-ups, F915) plus DVFS. Scaled desktop CPU time does not contain that cost.
  - Consequences: the proxy over-predicts phone gains from cuts in scene work, so treat such gains as an upper bound. A hand-off fix (single-threaded schedules) should show in `main_nonsim`, but its phone size is outside the calibration until one phone log of it exists.
  - After a GPU-only cut the phone would be main-bound at about 30-36 ms.
