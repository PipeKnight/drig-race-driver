They are owner-private and stay under `local/mac-logs/2026-11-25-2226/`. The analysis is in docs/PERFORMANCE.md, section "Mac run of 25 November 22:26" (F929). It was done with scratchpad scripts that grep and parse frame_stats; nothing was rebuilt or run on the PC.
- Crash [O]:
  - `Queue::submit` failed validation because `frame_split_readback` "is still mapped".
  - Then wgpu 29.0.4 `map_async` panicked ("Buffer is already mapped", range 0..112) and the game exited with code 1, 16.5 s into the race with the F9 counter on.
  - Cause in `frame_split::gpu_begin` [O]: a pending slot is freed without `unmap()` on the map-error path and on the 60-frame timeout path. wgpu resets a buffer's map context only in `unmap()`, as its source shows; wgpu 29 has no `map_state()`.
  - Which path fired is not known [I]. The log shows no earlier error, so most likely a map took more than 60 frames.
  - Proposed fix, not applied: `unmap()` on both paths, a per-slot "map outstanding" bit, and skipping the markers of a frame while the bit is set. A headless-device test would force the timeout and reuse the slot.
- Countdown [O]: both traces render at the 1440-row ceiling at 55-59 FPS.
  - The countdown is GPU-bound: acquire is 12.5-13 ms against 8.8-9.0 in the race, and main is 3 ms.
  - The smoothed frame time of about 17.2-17.9 ms sits in the hold band between ON_TIME 17.2 and LATE 18, so the first step down comes only after GO (windowed) or at "1" (fullscreen).
  - The 198-211 ms frame at the fade is in a window that also holds the last warm-up frames. No pipeline is compiled after Done.
  - Proposal, no default change: seed the race height from the warm-up frames, or count a GPU-bound countdown as late, using acquire as the Metal GPU signal.
