F840 Frame-split gpu_begin poll: removing it only moves the work into submit (2026-11-17, Claude Code).
- Goal (coordinator, item 3 of the F837 plan): `frame_split::gpu_begin` calls `device.poll(PollType::Poll)` on the render thread every frame while `FrameGpu` exists (1.1 ms per frame in the F837 profile build). The plan said to measure first whether wgpu only moves the same work elsewhere. Details: docs/PERFORMANCE.md "Frame-split poll (F840)".
- Reading wgpu-core 29.0.4: `Queue::submit` already ends with `device.maintain(fence, PollType::Poll, ...)`, which triages finished submissions and runs map callbacks, so the explicit poll looked redundant for the GPU-marker readbacks.
- Experiment: `gpu_begin` without the poll (the `RenderDevice` parameter removed), `cargo test --release -p grid-app --bin grid-app -- frame_split` 4 passed; binary `poll.exe` sha256 prefix 214A1F5BC3482E40 against the pushed F838 binary `f838.exe`. The readbacks still complete: 99.9 % of render frames got GPU markers (33006 of 33032; 100.0 % for f838), `g_bad=0` in both.
- A/B (RTX 4070, i7-12700, Vulkan, 1280x800 window, Fifo 165 Hz, `GRID_MESH_UPLOADS=0`; 5 alternating rounds per scene, idle-gated by process names, 0 busy starts; the same binary swung 60-107 fps between rounds, so the machine was noisier than for F838; pooled):

  | scene | variant | fps | 1 % low | worst window | main ms | render ms | GPU ms |
  |---|---|---|---|---|---|---|---|
  | derby route_8, native | f838 | 75.4 | 30-40 | 38.3 | 8.70 | 10.04 | 2.89 |
  | | no poll | 84.0 | 40-50 | 39.6 | 7.39 | 8.81 | 2.71 |
  | Donington route_0, native | f838 | 86.3 | 40-50 | 12.7 | 6.42 | 11.17 | 2.64 |
  | | no poll | 71.7 | 30-40 | 17.0 | 7.86 | 12.98 | 2.56 |

  Paired per round (no poll minus f838, `local/ab/paired.py po f838 poll`): `r_submit` +0.66 ms derby and +0.90 ms Donington, positive in all 10 pairs (+0.3 to +1.2); `r_encode` (which holds `RenderGraphSystems::Begin`) -1.32 derby, +0.25 Donington; render thread -1.22 derby (median -0.4), +1.80 Donington (worse in 4 of 5 pairs).
- Interpretation: the maintenance the poll did (submission triage, resource freeing, callbacks) now runs inside the next `queue.submit`; the cost is that work, not the extra call. No reliable gain, so the change is not kept; `frame_split.rs` is unchanged. Nothing to compare in images.
- To shrink it, the maintenance itself would have to get cheaper (fewer buffers or bind groups created and dropped per frame); that belongs with item 7 (remaining uploads) and a profile of `Device::maintain`.
